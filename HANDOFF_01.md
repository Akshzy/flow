# HANDOFF — PHASE 01

## Phase

Phase 01 — Technical Foundation

## Status

COMPLETE

## Summary

The repository contained project control documents only (no code, no git
history); the GitHub remote was empty, so the repository was initialized
locally and the documents were committed as the baseline. The documented
stack (FastAPI backend, Next.js frontend, PostgreSQL) was implemented as the
Phase 1 foundation, adapted to the actual environment (Windows, no Docker,
Python 3.14 + Node 24). The foundation is runnable, testable, and fully
verified against real PostgreSQL.

## Implemented functionality

- **Project structure**: `backend/` (FastAPI app, migrations, tests),
  `frontend/` (Next.js 15 + TypeScript + Tailwind 4), `scripts/pg.mjs`
  (embedded PostgreSQL lifecycle), `.github/workflows/ci.yml` (CI checks),
  `.gitignore`, `.gitattributes`.
- **Configuration** (`backend/app/config.py`): environment-driven via
  pydantic-settings (`ENVIRONMENT`, `DATABASE_URL`, `LOG_LEVEL`, `LOG_JSON`),
  optional `backend/.env` file; required values fail clearly at startup with
  a secret-free error (field names only); `backend/.env.example` with
  placeholders; `frontend/.env.example`.
- **Database foundation** (`backend/app/db.py`, `backend/app/models.py`):
  async SQLAlchemy 2.0 engine (psycopg 3 driver, pool_pre_ping, 5s
  connect_timeout), `ping()`, log-safe URL description (password redacted),
  minimal foundational `app_meta` table (migration machinery + round-trip
  verification; business schema deferred to later phases — ADR-003).
- **Migrations** (`backend/migrations/`): Alembic setup (URL resolved from
  `DATABASE_URL` env or `backend/.env`, clear failure when absent),
  migration 0001 (app_meta), CLI runs via `python -m alembic`.
- **Logging** (`backend/app/logging.py`): structlog; JSON output in
  production/test, console in development; redaction processor for sensitive
  keys; timestamps; level filtering.
- **Error handling** (`backend/app/errors.py`, `backend/app/main.py`):
  single error envelope `{"error": {code, message, details?}, "request_id"}`;
  handlers for AppError, HTTPException (404/405/...), RequestValidationError
  (422, whitelisted details — raw inputs never echoed), unexpected exceptions
  (500, generic message, stack traces logged server-side only).
- **Request-ID middleware** (`backend/app/middleware.py`): pure ASGI,
  server-generated IDs, context cleared per request, `X-Request-Id` response
  header, request logs with method/path (no query string)/status/duration.
- **Health/readiness** (`backend/app/main.py`): `GET /health` (liveness,
  no dependency checks) and `GET /ready` (verifies real database
  connectivity; 503 `database_unavailable` when down).
- **Frontend** (`frontend/`): single status page fetching `/health` with
  graceful "API unavailable" state (frontend/backend base integration).
- **Test infrastructure** (`backend/tests/`): pytest + pytest-asyncio +
  httpx (ASGI transport with lifespan); real PostgreSQL per session via
  `scripts/pg.mjs up --fresh` (clean database); `FLOWW_TEST_EXTERNAL_DB=1`
  switch for CI service containers.

## Security checks

- Secret scan: `git grep -iE "(password|secret|token|api[_-]?key)\s*[:=]\s*['\"]?[A-Za-z0-9]" -- ':!*.lock' ':!.env.example'`
  over tracked files → only placeholder/example references and test fixtures
  (throwaway local values like `postgres`/`super-secret-value` inside tests,
  never real credentials). No `.env` files committed (gitignored).
- `.env.example` files contain placeholders only (local default
  `postgres:postgres@127.0.0.1:55432` documented for the embedded database —
  a localhost-only throwaway, not a production secret).
- Logging redaction verified by tests and a live run; database URLs are
  logged with the password replaced.
- Validation error responses whitelist fields (raw input values never echoed).
- Client-supplied request IDs are not trusted (server-generated).
- The `pg.mjs` script prints connection info (including the local throwaway
  password) to stdout only at runtime for dev/test; never written to the repo.

## Known limitations

- The CI workflow (`.github/workflows/ci.yml`) has not been executed (no
  runner available); it runs the same locally-verified commands and uses a
  PostgreSQL 17 service container.
- No frontend unit test framework in Phase 1: the frontend scope is a single
  status page, verified via build/typecheck/lint and a live dev-server check.
  A test framework can be added when frontend logic grows.
- Windows event-loop policy for psycopg async is deprecated in Python 3.14
  (removal slated for 3.16); warnings suppressed in conftest/dev launcher —
  revisit when targeting a newer Python or Linux-only hosting (ADR-005).
- `alembic downgrade base` keeps the empty `alembic_version` table (standard
  alembic behavior; documented in the migration test).
- The embedded PostgreSQL data directory lives under `.pgdata/` (gitignored);
  it must not be committed.
- uvicorn's access logging (when enabled) includes query strings; no
  sensitive query parameters exist in Phase 1. Revisit in Phase 13 hardening.
